# 模块详设 · 企业微信推送与告警（alert）— 方法/类级

> 配合 `docs/AI开发提示词.md` §5.10。目标：把"失败聚合为告警 / 推送策略(门禁·去重·静默·升级) / 按客户分流 / 群机器人与自建应用 / 卡片渲染 / 重试与留痕 / 处置闭环 / 移动端"细化到接口与方法。

## 1. 职责
将检查失败按级别聚合为告警，按策略推送企业微信（@责任人），按客户/租户群分流到不同群；记录推送结果与处置闭环；为移动端提供 API。

## 2. 模型与接口

```java
enum AlertStatus { PENDING, PROCESSING, CLOSED }
enum WecomChannelType { WEBHOOK, APP }            // 群机器人 / 自建应用
enum WecomMsgType { MARKDOWN, TEXT, TEMPLATE_CARD }

record Alert(Long id, Long runId, Long checkResultId, Long customerId, String tenantKey,
             String ruleKey, Severity severity, String title, Map<String,Object> content,
             AlertStatus status, String assignee, String wecomPushStatus, Instant createdAt, Instant closedAt) {}

record AlertChannel(Long id, WecomChannelType type, String configCipher, WecomMsgType msgType,
             List<String> mentionMobiles, Severity gateSeverity, Duration dedupWindow,
             QuietHours quietHours, EscalationPolicy escalation, ChannelScope scope) {}

public interface AlertService {
    List<Alert> raise(DetectRun run);                  // 由调度/引擎在出现失败后调用
    void claim(Long id, String user);                  // PENDING→PROCESSING
    void transfer(Long id, String toUser);
    void close(Long id, String user, String note);     // →CLOSED
    Page<Alert> query(AlertQuery q);
}
public interface WecomPushService {
    PushResult push(AlertChannel ch, List<Alert> batch);   // 渲染+发送+记录, 失败重试
    PushResult test(AlertChannel ch);                      // 发测试消息
}
```

## 3. 失败聚合为告警（raise）

```
raise(run):
   fails = run.results where status in {FAILED, ERROR} (含 category=regression 的回归项)
   alerts = []
   for f in fails:
      alert = upsertAlert(run, f)        // 同 run+ruleKey 合并；写 alert 表(PENDING)
      alerts.add(alert)
   dispatch(alerts)                       // 进入推送策略
   return alerts
```

## 4. 推送策略（dispatch）— 核心

```
dispatch(alerts):
   for alert in alerts:
      ch = channelRouter.resolve(alert)          // 按 scope 分流: 客户专群 > 租户群 > 默认群
      if alert.severity < ch.gateSeverity: alert.wecomPushStatus=SILENCED; continue   // 仅 >=门禁推送
      if inQuietHours(ch) and alert.severity < CRITICAL: defer/或仅记录; continue       // 静默时段只推 CRITICAL
      if dedup(ch, alert): markMerged(alert); continue   // dedupWindow 内同规则合并为1条(附"另有N条")
      enqueue(ch, alert)                                  // 进推送队列(按 ch 聚合 5min 窗口合并发送)
   flushPush()    // 对每个 ch 合并 batch → WecomPushService.push

升级策略(定时巡检): CRITICAL 告警超过 escalation.timeout 仍 PENDING → 升级@部门主管并二次推送
```
分流路由 `channelRouter.resolve`：优先匹配"客户专属群"，否则"租户群规则"，否则"默认风控群"（见原型 wecom.html 的分流表）。

## 5. 企业微信对接与卡片渲染

```java
interface WecomClient {
    HttpResp sendWebhook(String webhookUrl, JsonNode payload);     // 群机器人
    HttpResp sendAppMessage(AppConf conf, JsonNode payload);       // 自建应用(需 access_token 缓存/刷新)
}
class WecomMessageRenderer {
    JsonNode render(AlertChannel ch, List<Alert> batch);  // 按 msgType 生成 markdown/text/template_card
}
```
卡片字段（参考 prototype/wecom.html）：级别徽标、客户/租户、检查名、问题、关联单据(凭证/差额)、影响、会计期间、时间、`@`责任人、查看详情链接。
- WEBHOOK：直接 POST `configCipher` 解密出的 webhook url；text 类型支持 `mentioned_mobile_list`。
- APP：用 corpId/secret/agentId 换取并缓存 `access_token`（提前刷新），调用应用消息 API；支持模板卡片。

## 6. 重试、留痕与幂等
```
push(ch, batch):
   payload = renderer.render(ch, batch)
   resp = retry(3, backoff){ client.send(...) }     // 网络/5xx/限流重试
   log = wecom_push_log(alertIds, ch, payload, resp.status, result, pushedAt)  // 留痕
   update alerts.wecomPushStatus = SENT/FAILED
   幂等键 = ch+alertIds+窗口, 防重复发送
```
失败：标 FAILED，进重试队列；可在告警中心查看推送状态并手动重推。

## 7. 处置闭环与移动端
- 状态机：PENDING →(claim)→ PROCESSING →(close)→ CLOSED；transfer 改 assignee。
- 移动端 API：`GET /mobile/alerts?status=`、`GET /mobile/alerts/{id}`、claim/transfer/close 复用同一 service，数据与 Web 一致（见原型 mobile-alerts.html）。

## 8. 逻辑完整性检查（自检）
- [ ] 失败(含回归)聚合为告警；同 run+规则合并。
- [ ] 仅 ≥门禁级别推送；dedup 窗口合并；静默时段只推 CRITICAL；升级策略生效。
- [ ] 按客户/租户群分流到不同群；@责任人(text 用 mobile, 卡片用对应字段)。
- [ ] WEBHOOK 与 APP 两通道；APP access_token 缓存与刷新；卡片字段完整。
- [ ] 推送失败重试 + push_log 留痕 + 幂等防重复；可手动重推。
- [ ] 处置闭环(认领/转交/关闭)与移动端 API 一致。
- [ ] 口令/webhook/secret 加密存取，不回显。

## 9. 关键单测
- 级别 < 门禁 → SILENCED 不推送。
- 5 分钟内同规则多次失败 → 合并为 1 条(附"另有 N 条")。
- 静默时段 HIGH 不推、CRITICAL 推。
- WEBHOOK 5xx → 重试 3 次后标 FAILED 并可重推；成功写 push_log。
- 客户专属群优先于默认群分流。
- CRITICAL 超时未处理 → 升级@主管二次推送。
- claim→close 状态流转；移动端与 Web 数据一致。
