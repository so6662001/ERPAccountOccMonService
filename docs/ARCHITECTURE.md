# ERP 账务正确性监测服务 — 架构与方法论

> 目标：在系统持续迭代的前提下，**守住账务数据正确性这条底线**，把"迭代引入的账务错误"在进入生产、影响经营之前拦截下来。

---

## 1. 问题本质

账务数据的正确性，本质上是一组**永远必须成立的恒等式 / 约束（invariants）**。
一旦某次研发迭代（改了一段取数逻辑、调了一个汇率算法、动了一张表结构）让其中某个恒等式不再成立，
就意味着账错了——而账错 = 直接的经济损失：

| 风险域 | 一旦被破坏的后果 | 对应的恒等式（举例） |
|---|---|---|
| 应收 / 应付 | 漏收欠款、坏账、对账不上 | 应收明细合计 = 应收总账科目余额 |
| 借贷平衡 | 凭证不平、报表错乱 | 每张凭证 Σ借 = Σ贷 |
| 余额连续性 | 期间结转错误、滚存错误 | 期初 + 本期借 − 本期贷 = 期末 |
| 成本核算 | 利润失真 → 利润分配出错 | 存货金额 = Σ(数量 × 单价)，单位成本 ≥ 0 |
| 跨系统一致 | 订单/财务/资金口径打架 | 订单系统应收金额 = 财务系统应收金额 |
| 数据完整性 | 孤儿单据、空金额、缺汇率 | 明细必有主单、金额非空 |

**核心洞察**：上述约束 90% 都可以表达成一条 SQL 断言：
- "某个标量必须等于另一个标量"（带容差）；
- "某个标量必须为 0 / 落在区间内"；
- "某个违规明细查询必须返回 0 行"。

因此监测服务的核心不是写死一堆规则，而是提供一个**声明式 + 可扩展的约束验证引擎**。

---

## 2. 两个监测时机（最关键）

正确性问题要在两个时机分别守住，缺一不可：

### 2.1 迭代回归防护（Regression Gate）——防"本不该变却变了"
挂在 CI / 发布流水线上，是抵御"研发迭代引入账错"的主防线：

1. **黄金主测试（Golden Master）**：在一份**冻结的标准数据集**上，让新版本跑出账务结果（试算平衡表、应收账龄、成本结转等），与旧版本/已审定的基线逐行对比。凡是"业务上不该变"的数字发生变化 → 阻断发布。
2. **基线指标对比**：对一批标记为 `invariant`（恒定）的关键指标（如某期收入合计、应收总额），把当前值与基线值比对，偏离超过容差即判定回归。

> 这正是你痛点的正解：**账务正确性跨迭代的保障 = 对账务"输出结果"做回归测试 + 对关键不变量做监测。**

### 2.2 生产持续监测（Continuous Monitoring）——防"数据已经错了"
定时（如每小时 / 每日结账后）在生产或准生产库上跑全部约束检查，
及时发现哪怕不是本次迭代引入、而是数据流转中产生的不一致，按严重级别告警 / 阻断结账。

## 3. 系统架构

```
                ┌─────────────────────────────────────────────┐
                │                  配置层 (YAML)               │
                │   datasources（多系统数据源） + checks（约束） │
                └───────────────────────┬─────────────────────┘
                                        │
        ┌───────────────────────────────▼──────────────────────────────┐
        │                          检查引擎 Engine                       │
        │   加载约束 → 逐条执行 → 捕获异常 → 汇总 CheckRun（含指标/样本）  │
        └───┬───────────────┬───────────────┬───────────────┬──────────┘
            │               │               │               │
   ┌────────▼──────┐ ┌──────▼───────┐ ┌─────▼──────┐ ┌──────▼────────┐
   │ 声明式 SQL 检查 │ │ 跨系统一致性检查│ │ 基线回归对比 │ │ 自定义插件检查 │
   │ 平衡/勾稽/连续/ │ │ 多数据源标量对比│ │ Golden/不变量│ │ (Python 扩展) │
   │ 成本/完整性     │ │              │ │            │ │              │
   └───────────────┘ └──────────────┘ └────────────┘ └──────────────┘
            │               │               │               │
        ┌────▼───────────────▼───────────────▼───────────────▼─────┐
        │     数据访问层 DataSource（SQLAlchemy：MySQL/PG/Oracle/    │
        │     SQL Server/达梦…，多源并存，按名引用）                  │
        └───────────────────────────┬──────────────────────────────┘
                                    │
        ┌───────────────────────────▼──────────────────────────────┐
        │   报告 Reporting（console / json / markdown）              │
        │   告警 Alerting（webhook / 钉钉 / 企业微信 / 邮件，可扩展） │
        │   退出码（CI 门禁：达到阻断级别则非零退出）                 │
        └───────────────────────────────────────────────────────────┘
```

### 核心抽象
- **DataSource / DataSourceManager**：对多套系统的数据库做统一只读访问，按名引用（跨系统一致性检查需要同时连多个源）。
- **Check（约束）**：一条可执行的检查，含 `key / 名称 / 类别 / 严重级别 / 数据源 / 执行逻辑`，产出 `CheckResult`。
- **CheckResult**：`status(通过/失败/错误/跳过) + 指标(metrics) + 违规样本(samples) + 信息 + 耗时`。违规样本让排查可以直接定位到具体单据。
- **Engine**：编排执行、异常隔离（单条检查报错不影响整体）、汇总成 `CheckRun`。
- **BaselineStore**：把一次运行的指标快照成基线；后续运行与基线对比，产出"回归"类发现。
- **Reporter / Alerter**：输出与告警，并据"门禁级别"决定退出码。

## 4. 约束分类与机制映射

| 约束类别 | 业务含义 | 落地机制（check type） |
|---|---|---|
| `平衡 balance` | 借贷必相等 | `scalar_zero`（全局 Σ借−Σ贷=0）、`rows_empty`（逐凭证不平） |
| `勾稽 reconciliation` | 总账=明细、模块间一致 | `scalar_equality`（明细合计=总账余额） |
| `连续性 continuity` | 期初+发生=期末、跨期衔接 | `rows_empty`（逐科目差额>容差） |
| `成本 cost` | 金额=数量×单价、成本非负 | `rows_empty`、`scalar_range` |
| `完整性 integrity` | 孤儿单、空值、缺汇率 | `rows_empty` |
| `跨系统 cross_system` | 多系统口径一致 | `cross_system_scalar_equality` |
| `回归 regression` | 不该变的数变了 | 基线指标对比（`invariant` 标记 + 容差） |

> 机制只有几种（标量等式 / 标量为零 / 标量区间 / 行集为空 / 跨源标量等式 / 基线对比），
> 但通过 SQL 的组合可以表达海量业务约束。复杂场景再用 Python 插件检查扩展。

---

## 5. 落地路线建议

1. **接入只读数据源**：为每套系统配置只读账号，写入 `datasources`。绝不允许监测服务写库。
2. **沉淀约束清单**：把财务/业务专家口中的"这两个数必须相等""这张表不该有这种记录"逐条翻译成 YAML 约束。这是最有价值的资产。
3. **挂上 CI 门禁**：发布前在冻结数据集上跑回归对比，`critical` 不通过则阻断合并/发布。
4. **生产定时巡检**：结账节点后定时全量跑，接入企业告警渠道。
5. **基线治理**：每次账务结果"合法变更"后，显式更新基线（带评审），形成可追溯的账务输出基线。
6. **持续扩充**：每修一个账务 bug，就补一条对应约束，杜绝同类问题复发（类似"回归用例越积越多"）。

---

## 6. 安全与边界
- 监测服务**全程只读**，不参与任何账务写入，避免成为新的风险源。
- 检查 SQL 应走只读副本 / 备库，避免给生产主库造成压力。
- 告警分级：`critical` 阻断 + 即时通知；`high/medium` 通知；`low/info` 仅记录。
