# 模块详设 · 灰度发布引擎（rollout）+ 模板差异同步 — 方法/类级

> 配合 `docs/AI开发提示词.md` §5.9 使用。目标：把规则/规则集/模板变更的"分批灰度生效、人工确认推进、自动回滚"与"模板差异对比+冲突人工决定"细化到接口与方法。

## 1. 职责
1. **灰度发布**：将某变更（规则/规则集/模板的新版本）按维度（服务器/客户/租户百分比）分批下发，每批观察期内监控误报率/错误率，**默认人工确认推进**，超阈值**自动回滚本批**并推送企业微信。仅对"版本达标"的目标纳入批次。
2. **模板差异同步**：计算模板新版本与客户本地配置的差异，对**冲突项逐条人工决定**（保留本地/采用模板），生成新版本，可接灰度。

## 2. 领域模型与状态机

```java
enum RolloutStatus { DRAFT, RUNNING, PAUSED, DONE, ROLLED_BACK }
enum BatchStatus   { PENDING, GRAYING, OBSERVING, PASSED, ROLLED_BACK }
enum RolloutDimension { BY_SERVER, BY_CUSTOMER, BY_TENANT_PCT }
enum AdvanceMode   { MANUAL, AUTO }     // 默认 MANUAL
enum SyncDecision  { KEEP_LOCAL, ADOPT_TEMPLATE, SKIP }

record RolloutStrategy(RolloutDimension dimension, List<BatchPlan> batches,
                       AdvanceMode advanceMode, int observeMinutes) {}
record BatchPlan(int seq, String scopeDesc, ScopeSelector selector, int observeMinutes) {}
record RollbackPolicy(BigDecimal falsePositiveRateThreshold,   // 默认 0.02
                      BigDecimal errorRateThreshold,           // 默认 0.05
                      String action) {}                        // 恢复上一版本+推送企业微信
```

状态机：
```
Rollout: DRAFT --start--> RUNNING --(全部批次 PASSED)--> DONE
         RUNNING --pause--> PAUSED --resume--> RUNNING
         RUNNING --(某批回滚/手动回滚)--> ROLLED_BACK
Batch:   PENDING --下发--> GRAYING --进入观察--> OBSERVING
         OBSERVING --(达标且人工确认/AUTO)--> PASSED
         OBSERVING --(超阈值)--> ROLLED_BACK
```

## 3. 服务接口

```java
public interface RolloutService {
    Rollout create(RolloutCreateCmd cmd);          // 选目标+维度+批次方案+回滚阈值，DRAFT
    Rollout start(Long rolloutId);                 // 下发第 1 批，进入 OBSERVING
    Rollout advance(Long rolloutId, String operator); // 人工确认推进下一批(MANUAL 必经)；校验当前批 PASSED
    Rollout pause(Long rolloutId);
    Rollout rollback(Long rolloutId, String reason, String operator); // 手动回滚(可回滚当前批/全部)
    RolloutView detail(Long rolloutId);            // 步骤条/批次进度/指标
}
```

下发与回滚的底层动作：
```java
interface RuleDeployer {
    void applyVersion(ScopeSelector scope, String targetRef, String toVersion);   // 对范围内目标启用新版本
    void revertVersion(ScopeSelector scope, String targetRef, String fromVersion);// 回滚到旧版本
}
```
注意：`ScopeSelector` 解析时**仅纳入版本达标目标**（复用 `VersionGate`）。

## 4. 推进与观察（核心流程）

```
start(id):
   r = load(id); assert DRAFT
   b1 = r.batches[0]; deploy(b1); b1.status=OBSERVING; b1.observeStartAt=now
   r.status=RUNNING; r.currentBatch=0; save

# 由定时器(每分钟)驱动观察评估，或在 advance 时即时评估
evaluateBatch(r, b):
   m = metricsCollector.collect(b.scope, b.observeStartAt)   // 执行数/失败/误报反馈/错误
   b.metrics = m
   if m.errorRate > policy.errorRateThreshold || m.falsePositiveRate > policy.fpThreshold:
        rollbackBatch(r, b, "超阈值自动回滚"); return
   if now - b.observeStartAt >= b.observeMinutes 且 指标达标:
        b.status = PASSED
        if r.advanceMode == AUTO: advance(r.id, "system")
        else: 等待人工 advance（前端显示"达标待确认"）

advance(id, operator):
   r=load(id); cur=r.batches[r.currentBatch]
   assert cur.status == PASSED  // 未达标不允许推进
   if 还有下一批: next=batches[++r.currentBatch]; deploy(next); next.status=OBSERVING; next.observeStartAt=now
   else: r.status = DONE
   audit(APPLY ROLLOUT advance by operator); save

rollbackBatch(r, b, reason):
   deployer.revertVersion(b.scope, r.targetRef, r.fromVersion)
   b.status=ROLLED_BACK; r.status=ROLLED_BACK
   wecom.pushRollback(r, b, reason)   // 推送研发值班群
   audit(ROLLOUT rollback)
```

误报率口径：`falsePositiveRate = 人工标记为误报的失败数 / 命中失败数`；`errorRate = ERROR 数 / 执行数`。由 `metricsCollector` 基于该批 scope 在观察窗内的 `detect_run/check_result` + 人工误报反馈聚合。

## 5. 模板差异同步

```java
public interface TemplateSyncService {
    DiffResult diff(Long customerId, Long templateId);            // from=本地基版, to=模板新版
    SyncResult apply(SyncApplyCmd cmd);                           // 含逐条 decisions，生成新版本
}

record DiffItem(String ruleKey, DiffKind kind, String summary,
                String localSpecJson, String templateSpecJson, boolean conflict) {}
enum DiffKind { ADDED, MODIFIED, DEPRECATED, LOCAL_CUSTOM }
```

差异计算：
```
for each rule key in (template ∪ localOverrides):
   in template not local            → ADDED
   in local not template            → LOCAL_CUSTOM (保留)
   in both, template changed         → MODIFIED
        if customer_rule.is_local_modified == true → conflict=true (本地也改过)
   template 标记弃用                  → DEPRECATED
```

应用规则（强约束）：
```
apply(cmd):
   for item in diff.items:
      decision = cmd.decisions[item.ruleKey]
      if item.conflict and decision == null:  reject("冲突项必须人工决定")   // 不允许默认覆盖
      switch decision:
        KEEP_LOCAL     -> 不变(保留本地)
        ADOPT_TEMPLATE -> 用模板规格覆盖 customer_rule，重置 is_local_modified=false
        SKIP/null(非冲突的修改) -> 跳过
      ADDED 默认随模板加入(可在 cmd 中排除); LOCAL_CUSTOM 永远保留; DEPRECATED 按决定停用
   生成 customer 维度新版本 + 审计; 返回可"接灰度发布"的句柄
```

## 6. 逻辑完整性检查（本模块自检）
- [ ] 三维度(服务器/客户/租户%)与分批方案可配；批次状态机完整(PENDING→GRAYING→OBSERVING→PASSED/ROLLED_BACK)。
- [ ] **默认人工确认推进**：达标也不自动放量，`advance` 必须校验当前批 PASSED；AUTO 为显式可选。
- [ ] 自动回滚：误报率>2% 或 错误率>5% → 回滚本批 + 推送企业微信 + 记录确认人/审计。
- [ ] 仅"版本达标"目标纳入批次(复用 VersionGate)。
- [ ] 暂停/继续/手动回滚(当前批/全部)可用；并发安全(同一 rollout 加锁)。
- [ ] 模板差异五类分类正确；**冲突项无人工决定则拒绝应用**；LOCAL_CUSTOM 永远保留；同步生成新版本并可接灰度。
- [ ] 全流程审计留痕。

## 7. 关键单测用例
- 3 批灰度：批1达标→人工 advance→批2；批2 误报率 3%>2% → 自动回滚 + 推送。
- MANUAL 模式下批次达标但未点 advance → 不放量。
- 模板 v2→v3：1 个 ADDED、1 个 MODIFIED(非冲突)、1 个 MODIFIED(本地改过=冲突)、1 个 LOCAL_CUSTOM；冲突未决定→apply 拒绝；决定 KEEP_LOCAL/ADOPT_TEMPLATE 后生成新版本。
- 版本过滤：`>=v4.0` 的规则在 v3.8 目标不纳入灰度批次。
